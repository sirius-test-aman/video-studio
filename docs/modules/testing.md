# Module: Testing (Testing Pipeline)

Sidebar label is **Testing**, subtitled "Test scenarios & Katalon pipeline". The
page itself is headed **Testing Pipeline**. Use "Testing" in narration; use
"Testing Pipeline" only when a frame shows the heading.

Turns a BRD into test scenarios, then turns those scenarios into Gherkin
`.feature` files generated by the developer's own AI IDE and delivered to
Confluence and a Git repository.

---

## What it does

**Two artifacts, produced in two different tabs.** Conflating them is the most
common error in describing this module.

**1 — Test scenarios, in the Confluence tab.** Select a Confluence page holding a
BRD; a **Generate Test Scenarios** button sits beside "View in Confluence" and
"Generate Jira Items", greyed until a page is selected. Generation opens a
document at `/sdlc/test-generation/<id>`, titled `Test Scenarios - <source page
title>`, with a **Push to Confluence** action. Once pushed, a toast confirms the
page was created and a **View in Confluence** button appears next to it.

**2 — Test cases, in the Testing tab.** Headed *"Testing Pipeline"*, described on
screen as: *select a test scenario document, generate an AI prompt, collect
Gherkin output, and deliver to Confluence + GitHub.* Velox writes the prompt and
receives the result; **the test cases themselves are generated by the developer's
AI IDE**, not by Velox.

The tab opens on **"Choose your testing workflow"** — *"Select how your AI IDE
sends test cases back to the platform."* Two paths:

| | **MCP Configured** | **MCP Not Configured** |
|---|---|---|
| Badge | Recommended | Manual workflow |
| Footer | Auto-receive via MCP | Manual copy & paste |
| Step 1 | Tell your IDE to generate test cases using MCP tools | Select scenario page → generate AI prompt |
| Step 2 | IDE auto-chains: find scenarios → get prompt → generate → submit back | Copy prompt → paste into your AI IDE → get Gherkin output |
| Step 3 | Gherkin auto-received here → review → push to GitHub / Confluence | Paste `.feature` output back → review → push to GitHub / Confluence |

The MCP path removes the copy-paste, and nothing else. Both paths end at the same
review-and-deliver screen. The choice is reversible — a **Change workflow** link
sits above the stepper.

## Who it is for

Quality Engineers, manual and automation. **Tech User** role. They arrive with a
BRD already in Confluence and leave with `.feature` files on a branch.

## The adoption blocker

**Feature awareness, with a specific shape: QEs do not know the BRD they were
never asked to read can seed their scenarios, or that their own IDE is the
generator.** The module looks like a test-authoring tool they would have to adopt
in place of their current one. It is not — it is a prompt factory plus a delivery
pipeline wrapped around the IDE they already use.

The GitHub Personal Access Token is a secondary barrier: real, and it stops people
at the last step rather than the first. Do not lead with it.

## What is genuinely true

Everything here is visible in a screenshot.

**Scenario document structure.** Header carries Document Version, "Based On" naming
the source BRD, and Status (Draft). Then `1. Overview`, `2. Test Scope` as a
bulleted list of in-scope behaviours, then the scenarios. Each scenario carries a
Priority and an Actor / Role, then **Objective**, **Preconditions**, **Happy Path
(Expected Flow)** as numbered steps, **Edge Cases**, **Negative / Error Cases**,
and **Expected Outcome**.

**Manual mode is two steps**, shown as a stepper: *Select Scenario Page & Copy
Prompt*, then *Paste & Deliver Test Cases*.

- The scenario-page dropdown is searchable and tags eligible pages **Scenario**, so a scenario document is distinguishable from a plain BRD in the list.
- On selection: *"Parsing scenarios… Analysing page with AI to extract test scenarios and build your prompt."*
- **Detected scenarios are listed and counted** — the captured run shows `DETECTED SCENARIOS (43)`, each with an ID (`TS-001`) and a one-line title.
- The generated **AI prompt is shown, not hidden**, with an Expand control. It opens *"You are a senior QA automation expert specializing in BDD test case generation"* and instructs the IDE to analyse all the code in the project — services, controllers, routes, models, utils — and produce implementation-level cases in valid Gherkin. **Copy Prompt to Clipboard**, captioned *"Paste this into Cursor, Claude Code, Copilot, or any AI IDE."*
- Pasted output is **validated on the spot**: *"Valid Gherkin syntax detected."*
- Test cases carry scenario tags (`@TS-001 @regression`) which is how they map back to scenarios.

**A coverage matrix, and it is a real count.** Labelled **Coverage Matrix**, showing
`17/43` with a progress bar, then per-scenario rows with a tick and a `1 test case`
count. This is *scenario coverage* — how many detected scenarios received at least
one test case — and it is displayed by the product.

**Export and delivery.**

- **Download test cases** as **XLSX**, **CSV**, or **CSV (per step)**. The CSV download lands as `test_cases.csv`.
- **Push to Confluence**, with the destination page title composed and shown before the push: `Test Cases - <project> - <scenario document title> - <date>`.
- **Push to repository**, with a **GitHub / Bitbucket** toggle.
- The `.feature` files are **named and listed before the push**, with a count — the captured run shows `18 .feature files will be pushed to Include/features/:` and every filename (`ts_001_submit_dispute_via_merchant_portal_with_complete_structured_data.feature` and so on), plus an `untagged_tests.feature` catching cases that carry no `@TS-` tag.
- Repository URL and **Branch Name** are both editable; the branch defaults to `test/auto-generated`.
- Pushing requires a **GitHub Personal Access Token saved once in My Profile → Integrations**. Until it is saved, the panel shows *"Connect GitHub to push from here"* with an **Open Profile** action and the push button stays disabled.

**Model and project are chosen at the top of the page** — the captured run shows
`Claude Sonnet 4.5` and project `Chargeback and Dispute Automation`.

## Where Katalon sits — and why it is out of scope

The chain, end to end:

```
Confluence BRD page ──> test scenarios doc ──> AI prompt ──> AI IDE ──> Gherkin .feature files
        ──> Confluence + Git repo ──> [Katalon runs them]
```

**The generated `.feature` files are Katalon-compatible.** Katalon is what
executes them, after the user has pushed to Confluence and connected GitHub or
Bitbucket. That execution is **outside the scope of a Velox tutorial** — the video
ends at delivery.

So Katalon is safe to name as the destination and must not be shown, demonstrated,
or explained as a step. On screen it appears only twice, neither a mechanism: the
sidebar subtitle "Test scenarios & Katalon pipeline", and a greyed placeholder in
the repository URL field reading `https://github.com/your-org/katalon-tests`.

`docs/products/velox.md` previously gave the input as `Stories + acceptance
criteria`, which no frame supports. That has been corrected: the artifact chain
there now reads BRD to scenarios to prompt to IDE to `.feature` files to
Confluence and a branch, with Katalon running them outside Velox.

## What we do not claim

- **Do not say Velox generates the test cases.** It generates the *prompt*; the developer's AI IDE generates the cases. Getting this wrong makes the product sound like something it deliberately is not.
- **Do not present the coverage matrix as code coverage.** `17/43` is scenarios-with-at-least-one-test-case. It says nothing about lines, branches, or product risk.
- **Do not imply full coverage.** The captured run covers 17 of 43 scenarios and produces 18 files from 43 scenarios. Partial coverage is the normal result, and the matrix exists precisely to show the gap.
- **Do not claim generated tests replace exploratory or manual judgement.** Status on the scenario document is *Draft*.
- **Do not imply Velox runs tests.** It writes files to a branch; Katalon runs them, outside the product. Naming Katalon as the destination is fine. Showing or explaining a Katalon run is out of scope.
- **Do not describe the MCP path as more capable.** It removes a copy-paste. Same prompt, same output, same review screen.
- **Do not imply anything is pushed automatically.** Confluence and repository pushes are separate explicit button presses, and the repository push is blocked outright until a token is saved.
- No percentages beyond the coverage count the UI itself displays. No time savings — the manual baseline is unmeasured.

## Safe emphasis

1. **Your IDE stays your IDE.** Cursor, Claude Code, Copilot, Rider — Velox hands it a prompt and takes the output back. Strongest answer to "another tool to learn".
2. **The gap is visible.** The coverage matrix shows which scenarios got cases and which did not, instead of implying the job is done.
3. **Traceability end to end.** BRD page → `TS-001` scenario → `@TS-001` tagged case → `ts_001_*.feature` on a branch. The ID survives every hop, and that is unusually easy to demonstrate on screen.
4. **Nothing is guessed at delivery.** File count, filenames, target path, branch and Confluence page title are all shown before you press anything.

## Vocabulary

| Say | Not |
|---|---|
| Testing / Testing Pipeline | Test module, QA module |
| test scenarios (the BRD-derived document) | test cases, when you mean scenarios |
| test cases (the Gherkin `.feature` output) | scripts, automation |
| Gherkin, `.feature` files | BDD files, cucumber files |
| coverage matrix | coverage report, coverage score |
| MCP configured / not configured | auto mode / manual mode as product names |
| your AI IDE | our IDE, the Velox IDE |

Both cards name the IDEs, and the two lists differ: the MCP-Not-Configured card
says *Copilot, Claude Code, Rider*; the caption under Copy Prompt says *Cursor,
Claude Code, Copilot*. **Name only what the frame on screen names**, or say "your
AI IDE".

## Screens worth showing

- **Moment of value:** the coverage matrix at `17/43` with per-scenario ticks. It is the one frame that shows the product being honest about its own output.
- **Strongest single frame:** the `18 .feature files will be pushed to Include/features/` list, filenames and all. Concrete, verifiable, and obviously not a mock.
- **The argument frame:** the "Choose your testing workflow" two-card screen. It states in the product's own words that the IDE is the generator.
- **Worth showing for traceability:** `DETECTED SCENARIOS (43)` with `TS-001`, then the pasted Gherkin tagged `@TS-001`, then `ts_001_*.feature` in the push list. Three frames, one ID.
- **Include, since this is a tutorial:** the "Connect GitHub" token warning and the Open Profile route. It is a real step a QE will hit, and a tutorial that skips it leaves them stuck at the last screen.
- **Not worth showing:** the "Parsing scenarios…" spinner. The AI prompt body at full length — one line of it establishes the point.

## Video plan

**One tutorial covering the whole flow.** Slug `testing-tutorial`; no `part`.

It spans two tabs, which is the one structural thing to handle deliberately:

```
Confluence tab          Generate Test Scenarios → scenario document → Push to Confluence
Testing tab             workflow choice → prompt → paste → validate → coverage matrix → deliver
```

The video opens in the Confluence tab. **Narrate that opening as "this is where a
scenario document comes from", not as a tour of Confluence** — the first third
otherwise reads as a Confluence video. Get to the scenario document, push it, and
move to the Testing tab.

The weight sits in the second half: the coverage matrix and the `.feature` file
list are the frames that carry the argument. Budget the Confluence half as setup.

No promo is planned yet. If one is later commissioned, the second half is the
material — "your IDE writes the tests" answers a real objection, and the coverage
matrix is more persuasive than another document-generation demo.
